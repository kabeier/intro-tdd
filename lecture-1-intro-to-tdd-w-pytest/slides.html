Why write tests first?

Reliability

The code does what the test says, so fewer bugs ship.

Documentation

A test shows exactly how the code should be used.

Maintainability

Refactor without fear: the tests catch what you break.

Collaboration

Many people change one codebase with confidence.

Regression

An old bug that comes back fails a test right away.

The test is the requirement, written as code.

The three errors from the lesson:

  • AssertionError: the check was False (an F).
  • Test discovery: "no tests ran", exit code 5 (wrong file or function name).
  • ImportError: a typo in a name, or the file isn't where Python looks (an E / exit 2).

def test_divide_by_zero():

Then in test_shopping.py change ["eggs", "milk", "jam"] to ["eggs", "milk"], save and run again.

Fake the keyboard, catch the screen test_input.py · test_print.py

** CODE ALONG, about 5 minutes. ** Students: test_input.py, test_print.py.

TYPE THIS, in order

test_input.py · part 1

def get_user_input():
    user_input = input("Enter a number: ")
    return int(user_input)

def test_get_user_input(monkeypatch):
    # Simulate user input
    monkeypatch.setattr("builtins.input", lambda _: "42")
    result = get_user_input()
    assert result == 42

test_print.py · part 1

def test_printing(capsys):
    print("Hello, pytest!")
    captured = capsys.readouterr()
    assert captured.out == "Hello, pytest!\n"

test_input.py · part 2 (add below, after a blank line)

def get_multiple_inputs():
    num1 = int(input("Enter the first number: "))
    num2 = int(input("Enter the second number: "))
    return num1 + num2

def test_get_multiple_inputs(monkeypatch):
    user_inputs = ["5", "7"]
    input_values = iter(user_inputs)
    monkeypatch.setattr("builtins.input", lambda _: next(input_values))
    assert get_multiple_inputs() == 5 + 7

Ctrl+S, then in the terminal:

pytest -v test_input.py test_print.py
  • monkeypatch swaps input() for a function that returns "42", so the test never waits for a keyboard.
  • capsys captures what was printed. Note the \n: print adds a newline.
  • Step 3: several inputs. iter + next hand them out one at a time.
  • You get monkeypatch and capsys by naming them as parameters. pytest fills them in.

The same tests, in a container

Dockerfile (in tdd-pytest/)

FROM python:3.11-slim

WORKDIR /app

COPY . .

RUN pip install --no-cache-dir pytest

CMD ["pytest"]
  • RUN runs while building the image (install things). You can have many.
  • CMD runs when the container starts. Here: the test suite, once.
  • --no-cache-dir: pip doesn't save a copy of its downloads → a smaller image
docker build -t pytest-tests .
docker run --rm pytest-tests
echo $?

Same Python, same pytest, on every laptop and in CI. Exit code 0 = green.

About 1 minute: explain the Dockerfile. The demo is on the next slide.

  • The Dockerfile is the curriculum's, word for word.
  • --no-cache-dir: normally pip saves a copy of every download (in ~/.cache/pip) to reinstall faster next time. In an image there is no "next time", so it's dead weight. Tested: 22.7 MB vs 24.5 MB for this layer (the cache was 1.9 MB). Small here, big with many packages. It's a habit you'll see in most Python Dockerfiles.
  • "This is exactly what a CI server does on every push. Lecture 2 shows the picture."

Now rebuild and run:

docker build -t pytest-tests .
docker run --rm pytest-tests
echo $?

Then in example.py change it back to num_one + num_two, save, rebuild, run.

  • Build → the steps from the Dockerfile. Run → CMD runs pytest inside the box: rootdir: /app, 8 passed. echo $? → 0.
  • Break it, run without rebuilding → still 8 passed. Ask chat: "Why?" (the image has the old copy: COPY happens at build time).
  • Rebuild, run → assert 0 == 4, 1 failed, 7 passed. echo $? → 1: the container passes pytest's exit code out. That's what CI reads.
  • Fix it, rebuild, run → green again.
